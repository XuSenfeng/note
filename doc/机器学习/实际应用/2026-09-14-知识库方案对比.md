# 知识库方案对比

### sqlite-vec

- 最轻，纯 C SQLite 扩展，无独立服务。
- 默认更像暴力搜索，不维护 HNSW 图，所以没有图内存。
- 支持 float32/int8/bit，量化后磁盘和缓存可大幅下降。
- 向量存 BLOB，可 mmap，RSS 不一定等于全量数据；但查询时页缓存会涨。
- 缺点：N 大时查询 CPU 线性增长，并发能力受 SQLite 限制。
- 适合：<10 万到几十万向量、内存 <256MB、边缘/本地应用。

纯C实现的SQLite扩展，**二进制大小仅约150KB**，无需额外依赖，非常契合嵌入式环境。它支持ARM NEON SIMD指令加速，能在树莓派4B这样的设备上将暴力搜索性能提升至**1.2ms**级别，对于个人文档库（通常几千到几万个分块）来说响应速度足够快

https://github.com/asg017/sqlite-vec
### turbovec

- 如果它走“量化 + SIMD + mmap”路线，资源可接近 sqlite-vec，甚至查询更快。
- 如果默认全内存加载向量和索引，则内存 = N×d×b + 索引开销。
- 关键看：是否 mmap、是否 int8/binary/PQ、是否构建 HNSW。
- 适合：想要比 sqlite-vec 快，又不想上 Qdrant 服务。

### zvec

- 按嵌入式向量库理解，通常无独立服务，但可能构建 HNSW。
- 若 HNSW 全内存：内存高于 sqlite-vec，约等于向量 + 图 + 元数据。
- 若支持 mmap/量化：可降到中低。
- 适合：单机嵌入式，但需要比暴力搜索更快的查询。

### Qdrant Edge

- 功能最全：过滤、payload、持久化、WAL、HNSW、量化、并发。
- 代价是资源最重：Rust 运行时 + 存储引擎 + 索引 + payload。
- 小规模可控制在几百 MB，大规模很容易上 GB。
- 开 scalar/binary quantization 可显著降向量内存，但图和 payload 仍在。
- 适合：边缘服务器、网关、需要过滤和稳定持久化的场景，不适合 MCU 级设备。

### qmd

- 更像应用层，不是单纯向量索引。
- 资源 = 底层向量引擎 + embedding 模型 + 文档解析 + 分块。
- 如果调用云 embedding：内存接近底层引擎。
- 如果本地 embedding：`MiniLM` 约 100MB 级，`bge-m3` 等可到 1–2GB+。
- 所以 qmd 的资源占用通常不能只看索引，模型才是大头。

### USearch

https://github.com/unum-cloud/usearch

它是一个可嵌入的ANN库，同样支持ARM NEON，并使用HNSW索引算法，速度更快，但代价是**内存占用会比纯暴力搜索的`sqlite-vec`稍高**
